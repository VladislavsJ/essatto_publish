# Geometry and gates fix blueprint QA

Four of the five failure areas can be fixed with deterministic code built on libraries already in the project venv (IfcOpenShell 0.9, shapely, PyMuPDF), and the fifth, symbol counting on scanned plans, needs one small trained detector, not a larger vision model. For IFC, the fix is a fallback ladder for every quantity (stored quantity, then representation parameters, then cached triangulated geometry) with unit scaling applied only to raw attribute values, because geometry already comes out in metres. For PDF schedules, the column shift disappears when words are assigned to cells by position inside a grid rebuilt from ruling lines; text order never enters. For CubiCasa, published evidence says vision-language models get only 16 to 39% of door counts exactly right, while a detector trained at 1024 px reaches about 90 AP50 on doors and windows, so training a detector on the public CubiCasa5k annotations is the right move. That comes with one decision the team must make openly: the hackathon images are the public CubiCasa5k images, so their exact ground truth is downloadable and training on them is training on the test set. For cost, a Haiku-tier planner behind a deterministic validate, repair, escalate gate is about 40 times cheaper per token than the current Opus, and the research estimates roughly a 30-fold cut per unknown question at a 10% escalation rate. Evidence strength varies: the IFC findings were measured on the project's own eight sample files, the PDF code was tested only on one synthetic schedule, and the detector accuracy and escalation rates are estimates until measured.

## IFC answers come from a fallback ladder, not one lookup

The research notes measured eight sample IFC files from the project dataset with IfcOpenShell 0.9.0.post1. Two of them have no quantity sets at all, four store lengths in millimetres, and exporters name the same quantity differently (ArchiCAD writes `BaseQuantities` even in IFC4, Revit 2013 writes a property set literally called `Dimensions`). A single lookup therefore fails often. Each quantity needs an ordered list of sources, and the answer should say which source was used.

### Units: scale raw values, never geometry

`ifcopenshell.util.unit.calculate_unit_scale(model)` returns the factor from file units to SI and accepts `"AREAUNIT"` and `"VOLUMEUNIT"` ([util/unit.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcopenshell-python/ifcopenshell/util/unit.py)). Shapes from `ifcopenshell.geom` are in metres regardless of project units unless `convert-back-units` is set ([geometry settings](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_settings.html)), while `get_psets` does no conversion ([util/element.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcopenshell-python/ifcopenshell/util/element.py)). In the notes' local measurements, **every millimetre file still used m² and m³ for area and volume**, so one global factor is wrong: scale by the measure type of each value (`IfcQuantityLength` and `IfcLengthMeasure` by the length factor, areas and volumes by their own). Values typed `IfcReal` carry no unit; one Revit pipe diameter of 0.1583 turned out to be feet, so numeric `IfcReal` "lengths" should be treated as untrusted.

### Lengths and volumes without quantity sets

For pipes, ducts, cable trays, beams and columns, the extrusion depth of the body representation is the length. `ifcopenshell.util.shape.get_extrusions` exposes it ([util/shape.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcopenshell-python/ifcopenshell/util/shape.py)). On the clinic plumbing model the notes measured that 2,883 of 2,893 pipe segments are a single extruded solid; summing `Depth` times the scale took **0.06 s and gave 3,240.77 m**, and the depth equalled Revit's own `Dimensions.Length` property exactly. Tessellating the same segments with the multiprocess iterator took 0.84 s on 12 threads, about 14 times slower. Bounding-box length is a last resort: it disagreed with the depth by more than 1 mm on 366 segments, by up to 0.6 m, because short segments are wider than they are long.

Walls are different. A wall's extrusion depth is its height, so wall length comes from a stored `Length` quantity first and the `Axis` polyline second. The two conventions disagree by about 4% on totals (1,166.0 m stored against 1,213.0 m by axis on one model), and the public ifc-bench ground truth for that model matches the stored value ([ifc-bench](https://huggingface.co/datasets/sylvainhellin/ifc-bench)). When no stored length exists, there is no way to know which convention a reference answer used; the answer should name the method.

The general fallback is one geometry pass per file with `ifcopenshell.geom.iterator` ([geometry processing](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html)), caching bounding box, volume and footprint polygon per GlobalId, keyed by file hash. Later questions become dictionary lookups. `get_volume` on default geometry equalled the stored `NetVolume` to two decimals for slabs on one model, but it needs a closed mesh, so results should be checked against `0 < volume <= bbox volume`. The notes did not time the two largest files (64 and 74 MB).

### Materials, layers and thickness

`get_material(el, should_skip_usage=True)` returns one of five shapes that each need a branch: `IfcMaterial`, `IfcMaterialLayerSet`, `IfcMaterialConstituentSet`, `IfcMaterialProfileSet`, `IfcMaterialList` ([util/element.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcopenshell-python/ifcopenshell/util/element.py)). Thickness exists only on layer sets. Revit IFC4 exports in the samples use constituent sets with no thickness, so thickness then falls back to a `Width` quantity, a named property (for example `Konstruktion.Breite`), a number parsed from the type name, or volume divided by side area. Three details matter in practice: the layer set's name attribute is `LayerSetName`, air-gap layers can have no material, and material names carry exporter ids that the benchmark answers strip ("Kalksandstein 2816491304" becomes "Kalksandstein"). This category deserves care: the ifc-bench authors report that **materials questions reach only 42% accuracy** for their agent because of nested material structures ([Hellin et al. 2026](https://arxiv.org/abs/2605.01698)).

### Generic properties need synonyms and a placeholder filter

`get_psets(el)` merges occurrence and inherited type properties and is the single entry point. The difficulty is naming and junk values. The same paper documents that door width appears as `Width`, `Rough Width`, `NominalWidth` and `Breite (B)` across exporters ([Hellin et al. 2026](https://arxiv.org/abs/2605.01698)). The notes found Revit exporting the property's own name as its value (`FireRating = 'Fire Rating'`) and ArchiCAD exporting `'<Wandmaterial>'`; the benchmark treats these as absent ([ifc-bench](https://huggingface.co/datasets/sylvainhellin/ifc-bench)). The fix is a regex synonym table per concept, searched over all property sets, plus a filter that drops placeholders. Door and window size should resolve as quantity, then `OverallWidth`/`OverallHeight`, then named properties, with a sanity check: one sample door had the two attributes swapped (2.27 wide, 0.95 high) while its quantities were right.

### Floor area and footprint: compute every variant and name the one used

No single definition reproduces reference answers. On the one model with published values, "Total Floor Area 2266.7 sq m" equals the **sum of `IfcSpace` gross floor areas**, and "Building Footprint Area: 537 sq m" equals the outline of the ground storey's slabs, walls and spaces with holes filled ([ifc-bench](https://huggingface.co/datasets/sylvainhellin/ifc-bench)). The union of all slabs gives 653 m² because roof overhangs inflate it, and the exporter's own building-level gross figure is 2,727 m². The dataset card describes another reference answer that sums six space areas because the model has no building-level value ([ifc-bench card](https://huggingface.co/datasets/sylvainhellin/ifc-bench)). The practical rule from the notes: prefer a stored building property, else sum space areas, else compute from geometry with shapely; report a second figure when variants differ by more than a few percent. This mapping is empirical, validated exactly on one model and within 2% on a second. The notes could not retrieve the standard definitions (buildingSMART pages returned HTTP 403).

### Spatial relations and multi-part answers

Explicit relations come first: `get_container`, `get_decomposition`, `IfcRelSpaceBoundary`, and `ifcopenshell.util.system.get_element_systems` ([util/system.py](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcopenshell-python/ifcopenshell/util/system.py)). In the samples the fallbacks are the common case. Spaces are aggregated to storeys, not contained; elements are almost never contained in spaces; the plumbing model has zero `IfcSystem` objects and carries system membership only as Revit properties such as `System Classification`. Storey falls back to bounding-box height against sorted storey elevations. Room membership falls back to `ifcopenshell.geom.tree().select_box(space)` for candidates, refined by a point-in-polygon test on the cached footprint ([geometry tree](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_tree.html)). The precise `tree.select(space)` returned nothing on the ArchiCAD sample and should not be relied on.

`ifcopenshell.util.selector` is a ready-made query language for the planner to target: `filter_elements(model, 'IfcDoor, Pset_DoorCommon.FireRating != NULL')` and value paths such as `storey.Name` or `/.*BaseQuantities/.NetVolume` ([selector syntax](https://docs.ifcopenshell.org/ifcopenshell-python/selector_syntax.html)). It does no unit scaling or placeholder cleaning, so it needs a wrapper.

For report-style answers, the ifc-bench grading explains what to output. An answer passes only if it is faithful, complete, relevant and transparent about "sources and methods", and exhaustive lists fail on any omission ([Hellin et al. 2026](https://arxiv.org/abs/2605.01698)). The same paper reports that an earlier fixed-toolset agent lost 45% of its failures to missing or incorrect tools. Two consequences follow: emit full enumerations with counts and percentages plus one line naming the source rung, and keep a generic escape hatch (synonym property search plus the geometry cache) for questions no tool anticipates. For visual evidence, the dataset's own plan SVGs already carry `data-guid` per element, so highlighting is an attribute edit and no rendering is needed.

## Cell geometry removes the schedule column shift

The shift has a simple cause. Splitting a text line on whitespace leaves no slot for an empty cell, and a two-row header ("WALLS" over "N E S W") yields fewer first-row tokens than leaf columns, so every value slides left. "AREA" returning "SF" fits "350 SF" being split into two tokens. Better tokenising cannot fix this; geometric assignment does.

Both pdfplumber and PyMuPDF build cells from ruling-line intersections ([pdfplumber README](https://raw.githubusercontent.com/jsvine/pdfplumber/stable/README.md), [PyMuPDF Page docs](https://pymupdf.readthedocs.io/en/latest/page.html)). The notes include a roughly 60-line grid builder on `page.get_cdrawings()` that treats thin filled rectangles as lines, tolerates fragmented segments, and merges cells where no separating edge is drawn, which recovers spanning headers that both libraries return as `None`. Words are then assigned to the cell containing their centre, and each leaf column is named by joining every header cell above it ("WALLS / N"). On one synthetic 10-column schedule this produced correct headers, kept empty cells in place and ran in 5 ms. **It was not run on the real failing sheet**, so the first task is to try it there.

Three practical points came out of the test. PyMuPDF kept rotated header text intact where pdfplumber scrambled it ("AERA"), so PyMuPDF is the better text source. `find_tables` dropped spaces inside cells, so text should be re-read with `get_text("words", clip=cell_bbox)`. The clip must be tight to the table, which `Page.cluster_drawings` or the schedule title position can provide. If a sheet has no vertical rules, column bands come from header-word extents and words are assigned by x-overlap, still not by order. If the text was exploded to vector outlines, which AutoCAD exports sometimes do, no words are extractable and OCR is unavoidable.

A deterministic alarm backs this up: score each column against a type regex (area, room number, finish code, dimension), re-score with columns shifted by one, and flag the table if a shift scores clearly higher. The check "AREA column contains only the string SF" catches the known symptom directly. The notes designed this check but did not run it. Table-structure models are a poor default: Docling's TableFormer takes **2 to 6 seconds per table on CPU** ([Docling report](https://arxiv.org/html/2408.09869)) and all published scores are on scientific or financial tables. They belong behind the alarm, if anywhere.

### Fixture symbols on vector plans remain the least proven piece

Learned symbol spotting works on its own dataset (SymPoint reaches 83.3 PQ on FloorPlanCAD) but was trained on 8 A100 GPUs for up to 1,000 epochs ([SymPoint](https://arxiv.org/html/2401.10556v1)), which rules it out. The notes propose a training-free route: cluster paths into fixture-sized instances with `cluster_drawings`, compute a rotation-tolerant signature (primitive counts, quantised lengths, aspect ratio), group identical signatures, and label each group once from a legend or tag. This is the notes' own design, **untested, with no accuracy estimate**. Its known weakness is fixtures drawn touching walls. The cheaper and more explainable check is to count fixture tags ("WC-1", "L-1") as text inside the room and compare with the fixture schedule quantity; a rendered legend symbol matched with OpenCV `matchTemplate` at four rotations is the raster fallback. Whether the target PDFs keep layers or reusable blocks should be checked first with `doc.get_layers()` and `page.get_xobjects()`.

## A 1280-pixel detector replaces the vision model for counting

The case against keeping a vision-language model for symbol counts is published. AECV-Bench tested ten models on 120 floor plans, some from CubiCasa5k. Exact-match door counts ranged from 0.09 to 0.39 and window counts from 0.03 to 0.34, with Claude Opus 4.5 at 0.16 on both; bedrooms and toilets scored far higher because text labels carry them. The authors conclude that symbol counting "remains unreliable for automation without tight human supervision or custom trained models" ([AECV-Bench](https://arxiv.org/abs/2601.04819)). That benchmark counts each door leaf separately, unlike this dataset, so its numbers are indicative.

### The test-set question comes first

The notes found that hackathon file names keep the public ids (`colorful-10052.png` is public folder `colorful/10052/`), and the public dataset ships a hand-made `model.svg` annotation for each image ([Zenodo](https://zenodo.org/records/2613548)). Three options follow. Training only on the roughly 213 public samples absent from the hackathon set is clean but far too little data. Training on the official 4,200-image train split and reporting on the 800 official validation and test images gives honest numbers; the notes recommend this. Training on everything maximises the score but memorises evaluation images. Whether the hackathon rules allow using the public annotations is not stated in the files the researchers read, so this should be confirmed with the organisers. The licence is non-commercial (CC BY-NC-SA 4.0 on Zenodo, CC BY-NC in the repo; the organisers apply the stricter one).

### Fit the counting convention before training

The answers were almost certainly generated from the SVGs, since conventions in the question text mirror SVG classes ("a double-bowl sink counts as one" matches the single `DoubleSink` icon in [house.py](https://github.com/CubiCasa/CubiCasa5k/blob/master/floortrans/loaders/house.py)). A short script that counts each distinct SVG class per image and finds which subsets reproduce each answer type settles what counts as a door, whether urinals count as toilets, and which sub-type is the leafless opening. Detector classes should then match those rules one to one. The repo's own `House` loader should not be reused: it drops non-4-corner icons and maps all shower classes to nothing, so the official pretrained weights cannot detect showers. No public converter covers toilets, sinks and showers; the notes estimate about 100 lines and one hour to write one.

### Model, resolution and training budget

Resolution dominates. A YOLO11s trained at 640 px reports 0.411 mAP50 on wall, door and window ([v1nz model card](https://huggingface.co/v1nz/yolo11-floorplan-det)), while RT-DETR-L at 1024 px self-reports **door AP50 89.8 and window 89.3** after 60 epochs in about 2.3 hours on two A100s ([rtdetr-floorplan-detector](https://github.com/OldDeLorean/rtdetr-floorplan-detector)). That model takes about 2 s per image on CPU. The notes recommend a YOLO26 or YOLO11 small or medium model at 1280 px with flips and 90-degree rotations, and estimate under 2 hours per run on one RTX 6000-class card; that estimate is extrapolated, not measured. YOLO26s runs in 87 ms on CPU at 640 px and has an NMS-free head ([YOLO26 docs](https://docs.ultralytics.com/models/yolo26/)), which removes one source of duplicate counts. Ultralytics models are AGPL-3.0 ([licence](https://www.ultralytics.com/license)); publishing the full repository satisfies it, and RF-DETR or D-FINE are Apache 2.0 alternatives. Door and window labels are thin wall footprints, often 5 to 15 px, so the thin side should be padded. For large sheets, SAHI tiled inference merges detections across tile seams, with intersection-over-smaller matching the usual setting ([SAHI guide](https://obss.github.io/sahi/guides/sliced-inference/)).

### Tune for the count, not for mAP

No paper reports exact-count accuracy for a trained detector on floor plans. The notes' own estimate is that 90 AP50 gives roughly 45 to 70% exact matches on doors and windows (a 10% per-object error over seven doors leaves about 48% of plans fully right) and 80 to 90% on toilets, sinks and showers, where there are only one to three per plan. The current "3 of 4 sinks" miss is in the class where a detector should help most. The levers are: choose each class's confidence threshold by maximising exact-match rate on held-out images, using the 85,514 CubiCasa question answers as calibration labels; evaluate doors only on the 3,519 images where doors are asked; and run the detector on four rotations as a self-check, marking the answer low-trust when counts disagree. About 20% of images show two or more floors, so counts run over the whole sheet. Room-type counts are a text problem first (MH, KH, WC, PARVEKE labels via OCR with a fuzzy vocabulary), with fixtures as a cross-check: sauna benches imply a sauna, a toilet without a shower in a small room suggests a WC.

## Door polygons and envelope geometry type DXF rooms

The research on this area is brief and rests on one published recipe. The Modified Swiss Dwellings dataset builds its room graphs geometrically with shapely and networkx: two rooms get a "door" edge when one door polygon lies within **0.05 m of both**, and a "passage" edge when the room polygons are within 0.04 m of each other ([MSD](https://arxiv.org/abs/2407.10121)). Applied to layered DXF, that means room polygons from the room layer, door footprints from door blocks, each door buffered by wall thickness plus about 5 cm, and an edge between the two rooms it touches. A door touching one room and the exterior is an entrance; a door touching more than two rooms means the buffer is too large. Every edge is explainable by pointing at the door.

For balcony against indoor, no published benchmark exists. The notes propose a rule over four features: the room lies outside or on the boundary of the heated-envelope outline, at least one side is a railing or thin line, it connects to a living room or bedroom through a door in an exterior wall, and it is small and shallow (roughly 1 to 2 m deep). This is inference, untested. A graph network is the fallback only if rules stall: a graph attention network reaches 0.893 validation accuracy on MSD room typing, but with zoning labels given as input ([MSD](https://arxiv.org/abs/2407.10121)), so geometry alone will score lower.

## A validated cheap planner cuts cost about thirty-fold

Prices read on 2026-11-14 put Claude Haiku 5.5 at $0.10 input and $0.50 output per million tokens, against $4 and $20 for Claude Opus 5.5 and $8 and $40 for Claude Fable 5.2 ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). The per-question figures below are the research notes' arithmetic for a 4,000-token cacheable prefix, a 50-token question and a 200-token plan, not published numbers.

| Model | No cache | Warm prompt cache |
|---|---|---|
| Claude Fable 5.2 | $0.0404 | $0.0092 |
| Claude Opus 5.5 | $0.0202 | $0.0050 |
| Claude Sonnet 5.5 | $0.0101 | $0.0025 |
| Claude Haiku 5.5 | $0.000505 | $0.000145 |

Structured outputs constrain the response to a JSON schema on every tier ([structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)), so plan validity is not a reason to stay on the large model. What the downgrade costs in accuracy is unknown: no published comparison of these models on text-to-plan tasks was found, and it has to be measured on the project's own questions.

### Validate after generation instead of routing before it

The cascade literature reports large savings (FrugalGPT claims up to 98% cost reduction at matched quality, a best case; [FrugalGPT](https://arxiv.org/pdf/2305.05176)), but learned routers need in-domain data: RouteLLM's routers were near random on out-of-domain benchmarks until such data was added ([RouteLLM](https://arxiv.org/html/2406.18665v4)). This project has something those papers lack, a deterministic verifier. The recommended order is rule parser, template cache, Haiku 5.5 with three to five retrieved verified plans, then a gate (every referenced level, name and type exists in the store; the plan executes; the result passes type and range checks), one repair turn with the error text, and escalation only after that. The repair turn is the one technique with consistent evidence: on BIRD text-to-SQL, execution-guided self-correction was the only component that helped every model, by 1.2 to 4.4 points, while self-consistency voting moved accuracy by at most 0.13 points at about five times the tokens ([arXiv 2606.29733](https://arxiv.org/abs/2606.29733)).

The notes estimate about $0.00067 per unknown question at a 10% escalation rate, roughly 30 times below uncached Opus 5.5. Escalation dominates the bill, so the lever is a lower escalation rate, not fewer Haiku tokens. The gate cannot catch a plan that executes and returns a plausible wrong value; that silent-error rate needs one measurement, by running both models over the dev set and comparing executed answers. Anthropic's own guidance adds a baseline worth one run before building anything: the large model at low effort with a warm cache, because a cascade forfeits cache reuse across models ([cost optimization](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)).

### Caching by template, not by embedding

Prompt caching is a prefix match with up to four breakpoints, and any byte change in the prefix invalidates it ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). The layout is system prompt, then the per-file store summary, then the question, with sorted JSON and a byte-identical schema; `usage.cache_read_input_tokens` confirms hits. For the plan cache, embedding similarity is the wrong key in a counting domain: "doors on level 2" and "windows on level 3" are near neighbours with different answers, and MeanCache reports 233 false hits on 700 queries for GPTCache's default threshold ([MeanCache](https://arxiv.org/pdf/2403.02694)). Masking entities into slots (`<LEVEL>`, `<TYPE>`, `<NUM>`) gives an exact key, typed slot re-binding, and one cached plan per question family. The same store serves as the few-shot pool: masked-question similarity scored 82.0 against 79.5 for random examples in DAIL-SQL's Spider tests ([DAIL-SQL](https://github.com/beachwang/dail-sql)). Templates that recur with the same plan can be promoted into the rule table; the notes found no published system that does this, so it is a design, not a replicated result.

Offline work moves cost out of the question path. The Batch API is 50% cheaper ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)) and suits lexicon expansion into the ten question languages and paraphrase pre-warming of the template cache. Vision belongs there too: an image costs up to 4,784 input tokens ([vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)), about $0.019 on Opus 5.5 by the notes' arithmetic, so perception should run once per file into a structured index.

### Distillation is a stretch goal

Vendor model cards claim a 0.6B student within 2 points of its teacher on text-to-SQL after about 10,000 synthetic pairs ([distil-labs card](https://huggingface.co/distil-labs/distil-qwen3-0.6b-text2sql)); these are self-reported. At $0.00015 per Haiku question, a local model saves little money. Its value is the "zero API cost" story for judges, and the notes doubt it fits in one to two days. A nearest-template classifier over masked questions gives the same property in a few hours and fails closed.

Cost should be reported per question as a distribution by answering tier, with the price card date, cold-cache results as the headline, the all-large-model baseline on the same questions, and offline costs stated separately. The competition's own definition of "low inference cost" (tokens, dollars, latency or model calls) was not available to the researchers and should be confirmed, because it changes which tier deserves investment.

## Conclusion: a prioritised implementation plan

The common thread is that each failure is a missing fallback or a missing check, not a missing model. Deterministic code with a stated source fixes accuracy and verifiability together, and it removes model calls, so three of the four judging criteria move in the same direction. The order below puts first the work that is deterministic, uses installed libraries and rests on measured evidence, and last the work whose payoff is unproven. Hour figures are the research notes' estimates where given; steps without a figure were not estimated.

| Priority | Work | Why here | Effort (notes' estimate) |
|---|---|---|---|
| 1 | IFC core: per-measure unit scaling; length, thickness, size and area ladders; placeholder filter and synonym search; material branches; one geometry pass cached per file hash | Measured on the project's own files; reproduces public reference answers; no model calls | Not estimated |
| 2 | IFC answers: full enumerations with counts, one line naming the source rung, "not available" plus nearest proxy; highlight by `data-guid` in the supplied SVGs | Matches how ifc-bench style grading scores completeness and transparency | Not estimated |
| 3 | PDF schedules: run the grid builder on the real failing sheet, cell-centre word assignment, header concatenation, shift alarm | Small code, already in the venv; only proven on a synthetic sheet, so test first | Not estimated |
| 4 | Cost baseline and planner: log four usage meters per question; prompt caching with two breakpoints; Haiku 5.5 planner with gate, one repair turn, escalation; measure escalation and silent-error rates | Largest measured price gap; the gate also raises verifiability | About 8 h |
| 5 | CubiCasa detector: confirm rules on public annotations and choose the train/test split; fit conventions from SVG classes; write the converter; train at 1280 px; tune per-class thresholds for exact match | Biggest expected accuracy gain on symbol counts, but depends on a rules decision and unmeasured accuracy | Converter about 1 h; under 2 h per training run |
| 6 | Template cache with slot re-binding, few-shot retrieval from verified plans, offline lexicon expansion and paraphrase pre-warming, rule promotion | Raises the share of questions answered with zero model calls | About 7 h |
| 7 | DXF: door-buffer adjacency edges and the four-feature balcony rule | Simple and explainable, but evidence is thin and the balcony rule is untested | Not estimated |
| 8 | Stretch: PDF symbol signatures or template matching; nearest-template classifier or distilled local planner; room segmentation; table-structure model behind the alarm | Unproven payoff or more than a day of work | Open |

Three open questions should be answered before effort is committed, because each can reorder this list: whether the organisers permit training on the public CubiCasa5k annotations, how they define inference cost, and whether the real schedule sheets have ruling lines and extractable text. Two numbers will then show whether the plan worked: the exact-count rate on held-out CubiCasa images, and dollars per correct answer on a cold cache against the all-large-model baseline.
